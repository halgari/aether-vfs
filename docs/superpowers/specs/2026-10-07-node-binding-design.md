# Node.js binding — Design Spec

**Status:** Approved design, not yet implemented.
**Date:** 2026-10-07
**Consumer:** Vortex (Electron). Main use: overlay mod folders read-only on top of each other, with a
write folder for overwrites, and launch the game or a tool through that view.
**License:** GPL-3.0-only, like everything else here. Vortex is GPL-3.0.

---

## 1. Goal and constraints

- Node drives aether-vfs **as a host**: it builds a session from folders, starts serving, launches a
  program, watches the launch and stops it.
- **Node does nothing OS-specific.** Every platform difference is in Rust, behind `vfs-embed`. The
  JavaScript API is identical on Windows and Linux (Proton).
- **Isolated.** The binding lives outside the `rust/` workspace. The core build, tests and CI do not
  change, and the binding depends on nothing but `vfs-embed`'s public API.
- **Distributed as prebuilt npm packages.** Vortex installs with npm and needs no Rust toolchain.

Out of scope: providers written in JavaScript, zip and storage layers, the registry overlay, and the
`vfs` daemon. None of these is precluded by this design; each can be added later.

History: an earlier napi addon (`rust/crates/vfs-node`) was removed in `1f40e17` as not needed yet. It
lived inside the workspace and was mostly JavaScript-provider machinery, which this design drops.

## 2. Layout

```
bindings/node/
  Cargo.toml          # crate `aether-vfs-node`, cdylib, depends on vfs-embed by path
  src/                # napi-rs: type conversion and threading only
  index.d.ts          # generated by napi-rs
  package.json        # @aether-vfs/node (loader)
  npm/win32-x64/      # @aether-vfs/node-win32-x64: .node + vfs_shim_dll.dll + vfs-injector.exe
  npm/linux-x64/      # @aether-vfs/node-linux-x64: the same set
  test/               # node:test, TypeScript
```

The crate is its own Cargo project (not a member of `rust/Cargo.toml`). It uses napi-rs, whose N-API
is ABI-stable, so one build serves Node and Electron. `@aether-vfs/*` are placeholder names until
the npm scope is chosen.

## 3. JavaScript API

```ts
import { Session } from '@aether-vfs/node';

const session = new Session({
  stateDir: 'D:\\vortex\\aether\\skyrimse',     // ring, config, staging bookkeeping
  roots: [
    {
      dir: 'D:\\vortex\\aether\\skyrimse\\game',   // empty directory the VFS takes over
      layers: [                                     // lowest priority first, all read-only
        'C:\\Steam\\steamapps\\common\\Skyrim Special Edition',
        'D:\\vortex\\mods\\SKSE',
        'D:\\vortex\\mods\\SkyUI',
      ],
      writeTo: 'D:\\vortex\\overwrite\\game',      // new and changed files land here
    },
  ],
  proton: { steamClient: '/home/u/.local/share/Steam', appId: 489830 }, // optional; ignored on Windows
});

await session.start();
session.roots();                                     // [{ dir, programPath }] where the program sees each root

const run = await session.launch({
  image: 'skse64_loader.exe',                        // relative to root 0, or absolute
  args: [], env: {}, stageAlso: ['SkyrimSE.exe'],
  activation: 'import',                              // default; 'inject' to force injection
});
run.pid;
run.notes;                                           // string[]: fallbacks, refused children, warnings
const end = await run.exited;                        // { kind: 'exited', code } | { kind: 'stopped' }
await run.stop();

await session.setLayers(0, newLayers);               // between launches only
await session.close();
```

Rules:

- **Roots are host directories** on both platforms. On Windows the program sees a root at `dir`. Under
  Proton, Rust links it into the prefix at a stable `C:\` path, which `session.roots()` reports as
  `programPath`. Node never handles a Wine path.
- **The base game is the lowest layer.** There is no deployment or hard-linking.
- **One launch at a time per session.** `launch` while a launch is running, or `setLayers` while one is
  running, rejects with `E_STATE`. A tool can be launched once the game has exited.
- **`run.exited`** resolves when the whole launch has ended, not just the first process:
  `skse64_loader.exe` exiting while `SkyrimSE.exe` runs is still a running launch.

## 4. Threading, errors, lifetime

**Threading.** The `Session` is held in Rust behind a mutex. `start`, `launch`, `setLayers`, `close`,
`run.exited` and `run.stop` run on napi-rs's worker pool and return Promises. The JavaScript thread
only queues work. Nothing calls back into JavaScript from inside the VFS, so there is no re-entrancy
and none of the old addon's deadlock guards are needed.

**Errors.** Every rejection is an `Error` with a stable `code` and the full Rust message:

| code | meaning |
|---|---|
| `E_CONFIG` | bad or overlapping path, missing layer folder, root `dir` not empty or not creatable |
| `E_ARTIFACTS` | the shim DLL or injector is missing beside the addon |
| `E_STATE` | launch while running, `setLayers` while running, any call after `close` |
| `E_LAUNCH` | the program failed to start or was refused; message carries the injector's report and refused children |
| `E_PROTON` | no GE-Proton runtime, prefix setup failed, Steam not running |
| `E_INTERNAL` | anything else, including a caught Rust panic |

Things that are not failures (activation fell back to injection, NVAPI warnings, refused child
processes) go to `run.notes`, never to exceptions. A panic in Rust is caught at the napi boundary and
becomes `E_INTERNAL`; it never aborts Electron.

**Lifetime.** `close()` stops a running launch, then stops serving; it is idempotent. If a `Session` is
garbage-collected without `close()`, its finalizer does the same. If the process dies outright,
aether-vfs's existing rules apply: staged files are swept on the next start. A `Session` belongs to the
thread that made it.

## 5. Changes to `vfs-embed`

The existing API stays (Haskill and `vfs-directord` use it). Three additions:

1. **`Session::add_root(dir) -> RootId`**, a host directory on every platform. Windows: the program
   sees the root at `dir`. Proton: Rust chooses a stable location in the prefix (derived from the state
   directory) and links `dir` there. `root_locations()` reports it. Built on `set_root` and
   `declare_root`, whose current (per-platform) meanings do not change.
2. **`launch_detached` and `LaunchHandle` on Windows.** Today they exist only on the Proton path. On
   Windows the launch is started in a Job Object, so every descendant process belongs to it. The launch
   is running while any process in the job is alive; `stop` is `TerminateJobObject`. Same type and
   methods on both platforms: `pid`, `notes`, `try_wait`, `wait`, `stop`, `stopper`.
3. **`Session::set_proton(ProtonOptions)`**, compiled on every platform and ignored on Windows.
   `ProtonOptions { home, prefix_name, steam_client, app_id, steam_helper }` maps onto the existing
   Proton setters; unset fields keep today's defaults.

The binding uses only: `Session::new`, `set_state_dir`, `add_root`, `mount_at` with read-only
`DiskProvider`s, `set_write_layer_at`, `clear_root`, `set_proton`, `serve`, `launch_detached`,
`LaunchHandle`, `root_locations`, `stop_serve`, and `LaunchOpts`. A seam test in the binding fails if
it names anything else.

## 6. Testing

1. **`vfs-embed`:** unit tests for `add_root` on both platforms. Proton end-to-end: the fixture launch
   through `add_root` and `launch_detached`. Windows: a fixture that spawns a child, where `try_wait` is
   `None` until both have exited and `stop` ends both.
2. **Binding, Rust:** the seam test, and a test that every error path maps to its `code`.
3. **Binding, JavaScript (node:test, TypeScript):**
   - API without a game: lifecycle, `E_STATE` and `E_CONFIG` rejections, `close()` idempotent,
     finalizer cleanup.
   - Launch: two layers and a write folder; `vfs-fixture-read` must read the top layer's copy of a file,
     and its write must land in `writeTo`. Runs under Proton on Linux and natively on Windows.
   - Skyrim: opt-in through `VFS_TEST_SKYRIM_DIR`, skipped otherwise.

Windows behaviour (Job Objects in particular) is verified on a real Windows CI runner; cross-building
and running under Wine locally is a smoke test, not a substitute.

## 7. CI and packaging

- A new `node` CI job builds the addon for `linux-x64` and `win32-x64`, and runs the JavaScript tests
  on Linux (with the cached GE-Proton the `proton-linux` job uses) and on a Windows runner. The
  `rust/` jobs do not change.
- Packages follow napi-rs's layout: the loader `@aether-vfs/node` with optional platform packages
  `@aether-vfs/node-win32-x64` and `@aether-vfs/node-linux-x64`. Each platform package carries the
  `.node` addon, `vfs_shim_dll.dll` and `vfs-injector.exe`; the addon finds them beside itself.
- Releases are tagged and published from CI. Publishing needs the owner's go-ahead.
- All packages are GPL-3.0-only.
