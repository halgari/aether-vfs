# Documentation audit — `feat/stage4-embed`

**Verdict: the two evidence artifacts and the new benchmark write-ups hold up well, but the two design specs have not been maintained against the code this branch shipped — five statements in them are now false, including one that would have a reader undo a deliberate, measured decision, and one that misreports the shim's panic safety.**

Scope: `docs.diff` read in full, then the current files. Cargo commands run from `C:\oss\aether-vfs\rust`. Cheap verifications were run (greps against source, `cargo metadata`, `tsc --noEmit`, `check-types.mts`, the vitest suite, `node examples/vertical-slice.cts`, a fresh `tsc --emitDeclarationOnly` diffed against the on-disk `index.d.cts`). The injected e2e suite was not run — it exceeds ten minutes and locks the shim DLL.

## Critical

### C1 | `docs/superpowers/specs/2026-08-13-pluggable-providers-design.md:704-721` (§8c) — the cache-defect section is stated as live, and its recommendation was reversed by later measurement in this same branch. **VERIFIED.**

The section reads in the present tense throughout:

- `:708` — *"`vfs-cache/src/store.rs:120` **clones the whole block on every hit**, so a 4 KiB read memcpys 1 MiB."*
- `:714` — *"an O(n) LRU scan per hit (`store.rs:116-118`), and one process-wide mutex (`store.rs:59`)"*
- `:718` — *"**A 64 KiB block is the best configuration measured (1094 MiB/s.)**"*
- `:719-721` — *"No existing test catches any of this… every cached read in every session pays it today."*

All four are false as of this branch:

- `rust/crates/vfs-cache/src/store.rs:48` — `pub type Block = Arc<[u8]>`; a hit is a refcount bump and the caller copies only its own range, after the lock is released (`store.rs:11-15`).
- CLOCK second-chance replaced the LRU deque; a hit sets one `AtomicBool` reference bit and never touches the ordering (`store.rs:16-21`, `:90-96`).
- The mutex is gone: `store.rs:142` is `shards: Box<[RwLock<Shard>]>`, and the hit path takes the **shared** lock (`store.rs:253-254`). Hit counters moved onto the shard.
- The cited line numbers now point at unrelated code (`store.rs:59` is inside `CacheConfig`).
- Two tests exist, added in this branch: `crates/vfs-cache/tests/hit_copy_cost.rs`, `crates/vfs-cache/tests/hit_scaling_cost.rs`.
- The 64 KiB recommendation was **reversed**: `crates/vfs-cache/src/lib.rs:18-39` keeps `DEFAULT_BLOCK_SIZE = 1 MiB` and explains that the old sweep "was measuring the clone"; `rust/docs/benchmarks/block-cache-hit-cost.md:57-64` records 64 KiB and 1 MiB at parity post-fix. A reader following §8c would change the default and undo that decision.

Note the contrast, because it shows this was an omission rather than a policy: `rust/docs/benchmarks/node-ffi-round-trip.md:3` opens with *"Status: historical"*, and §8b's rule 1 carries an explicit *"Corrected 2026-08-17 by measurement"* block. §8c got neither.

### C2 | `…pluggable-providers-design.md:912-921` (§13) and `…no-bypass-and-real-roots-design.md:508` — both specs say hook-boundary `catch_unwind` was never implemented and that a hook panic now unwinds *further* than it used to. **VERIFIED false.**

§13: *"That wrapping was never implemented… Until hook entry points actually call `catch_unwind`, a hook panic unwinds further than it used to."* No-bypass `:508`: *"Hook-boundary `catch_unwind`, still unimplemented (see the Stage 1 spec)."*

`rust/crates/vfs-shim/src/hook.rs:146-162` defines `contain_panic` around `catch_unwind(AssertUnwindSafe(body))`, and the `hook_entry_points!` macro (`hook.rs:174-190`) routes **every** `extern "system"` detour through it — enforced by a source-scanning test, `no_extern_hook_bypasses_the_panic_containment_macro` (`hook.rs:4935`), which requires the macro to be the only definer of `extern "system"` fns in the file. `lazy_section.rs:726` carries its own. `hook.rs:100-115` documents the outcome the spec denies: *"what the game gets now is a returned status instead of a dead process."* This is the most dangerous of the stale statements because it describes the injected component's safety posture as worse than it is.

### C3 | `…pluggable-providers-design.md:349` (§6) — claims the router's read/readdir asymmetry "has dedicated conformance cases". **VERIFIED false, and it is a claim of test coverage that does not exist.**

`RouterProvider::readdir` is single-dispatch — `crates/vfs-compose/src/router.rs:71-74` returns only `self.provider_for(path).readdir(p)`, and the type's own doc says so (`router.rs:24-26`). Both conformance runs over the router are constructed with **zero routes** (`router.rs:177-183` and `:192-197`, both `RouterProvider::new(default, vec![])`), so no conformance case exercises the asymmetry at all. `crates/vfs-embed/src/session.rs:816-822` independently records the gap: *"`router`'s listing is **single-dispatch** rather than the union §6 specifies — so a file served by a route is readable by name and absent from its own directory."*

### C4 | `…no-bypass-and-real-roots-design.md:482` and `:506` — the deferral/gap lists contain three items that are implemented. **VERIFIED false.**

- `:482` — *"The director's `ops_write` and `total_write_bytes` counters exist in code but are **printed by no report**, so there is currently no way to observe under-root write activity short of grepping raw shim logs."* `crates/vfs-director/src/io_stats.rs:295` prints `write={} write_bytes={:.2} MiB` on the aggregate line and `:321` per path, with a regression test named for this exact prerequisite (`write_ops_and_bytes_are_surfaced`, `io_stats.rs:435`). `rust/docs/bypass-baseline.md:597-609` already records the closure — so the two documents contradict each other.
- `:506` — lists *"the read-write `memory` provider"* and the *"rejected-write discovery workflow"* as deferred. `crates/vfs-compose/src/memory.rs:127` declares `Access::ReadWrite` and is conformance-clean over the write cases (`memory.rs:304-310`); `Session::rejected_writes()` exists (`vfs-embed/src/session.rs:765`) with a seam test asserting discoverability (`vfs-embed/tests/embed_api.rs:192-227`). Correctly still deferred, verified: `dry_run_writes`, `FLAG_WRITE_BULK`, and the remote provider's write half.
